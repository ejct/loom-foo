# Creative Reasoning

## Named specialist composition (optional, not a dispatcher)

This skill may contribute a conceptual mechanism to `loom-foo-design`, `loom-foo-icon-design`, `loom-foo-experience-design`, `loom-foo-architecture-design`, `loom-foo-drafting`, `loom-foo-narrative-design` or `loom-foo-proposal-refinement`. Those specialists still own the requested artifact, constraints, implementation and validation; Creative Reasoning owns a bounded conceptual decision only when ideation itself is the task. A named relationship means **possible method composition**, never a required sub-agent call, a dependency, or confirmed runtime invocation.

For cross-skill use, establish the subject owner and the smallest unresolved conceptual question; retain `FIXED` constraints and user authority, supply a materially different valid principle with risks, hand it to the original owner, and return to production. If the owner already has an adequate solution, skip this skill. Do not escalate local geometry, tool failures, missed constraints, ordinary alternatives or settled execution. Exact skill IDs document relationships; do not infer that source mentions automatically trigger a host skill.


## Contract and boundary

**Purpose:** selectively improve the *search for a useful solution principle* while preserving the user's requested output. This skill owns conceptual search, reframing, fixation recovery and a bounded concept recommendation **when those are the requested output**. It never owns the finished icon, interface, code, research findings, written article or implementation merely because creativity helps produce it.

The subject owner retains production, permissions and verification: e.g. Icon Design for app icons, Experience Design for UX, Architecture Design for system architecture, Drafting/Narrative Design for writing. Do not force-load these skills or invent a global routing/orchestration layer. A user asking for a finished artifact should receive that artifact when tools allow, **not a mandatory Concept Exploration Note**.

**Activation:** an explicit request for alternative conceptual directions/reframing/synthesis; an unresolved substantive concept choice where different principles matter; or repeated attempts sharing the same rejected *conceptual* mechanism. A user reporting repetition is a signal to diagnose, **not proof of concept fixation**. Where the subject owner can resolve a local issue without new concepts, do not activate this skill. A generic adjective such as "creative" or the mere complexity of a task is not sufficient.

**Non-triggers:** exact localized edits, approved design refinement at execution level, ordinary tool-generated images, evidence retrieval/fact-checking, isolated style adjustments, standalone review, accepted engineering implementation, or creative novelty that would violate approved requirements. Avoid speculative creativity for safety-critical or evidence-bound conclusions.

## Fast path — choose only the necessary mode

1. **Protect the contract.** Recover requested result; separate `FIXED` constraints, `FLEXIBLE` variables and material `UNKNOWN` assumptions. Preserve source evidence, approved geometry/behavior, privacy, cost, permission and exact output medium. User authorization, not a creative idea, governs changes. If no meaningful freedom remains, return to the output owner.
2. **Identify the situation and choose a mode** (one can be enough):
   - **REFRAME:** the problem representation or assumed goal blocks useful alternatives; change the *question*, but not the user's accepted objective or invariants.
   - **DIVERGE:** the space of valid solution principles is open; explore structurally/causally different options, optionally drawing from genuinely different knowledge domains or lived contexts.
   - **UNSTICK:** attempts repeat a failed principle; first diagnose whether the cause is a **concept**, **representation**, **tool**, **constraint retention**, or **evaluation** failure. Only concept-level failures require novel concepts.
   - **SYNTHESIZE:** two or more valid ideas each solve different parts; combine mechanisms only if their assumptions and constraints are compatible.
   - **CONVERGE:** enough options exist; distinguish *novelty* from *usefulness*, filter invalid candidates and select a justified direction (or state the decisive unknown).
3. **Work proportionately.** State the smallest creative decision; use one meaningful pivot if adequate. Do not mandate a mode sequence, idea quota, role-playing session, external research or multi-agent run. Treat a cross-domain analogy as a hypothesis requiring target-fit checks, not proof.
4. **Return to production.** When ideation itself is the requested deliverable, provide concise mechanisms, trade-offs and a recommendation or discriminating question. Otherwise hand the selected principle back to the existing output owner and execute the requested artifact where supported. Preserve the source/approved base; don't regenerate unrelated parts to disguise an unresolved local defect.
5. **Stop intentionally.** Stop exploring when a valid direction has been accepted or implemented, when no meaningful conceptual choice remains, or when further options would add noise. Resume only for a new explicit ideation request, genuinely failed principle or changed requirement. A failed render does not automatically reopen an accepted concept.

## L2 references — event-triggered

- For **REFRAME** or **DIVERGE** when different problem representations or knowledge domains could change the choice, read `references/EXPLORATION_AND_PERSPECTIVES.md`.
- For repeated rejected attempts or a proposed **UNSTICK** intervention, read `references/FIXATION_AND_FAILURE_DIAGNOSIS.md` before recommending a pivot.
- For nontrivial **SYNTHESIZE**/**CONVERGE** decisions where options have real incompatibilities, novelty/usefulness tension or consequential trade-offs, read `references/SYNTHESIS_AND_CONVERGENCE.md`.
- For a simple conceptual request with a clear valid next idea, the root fast path is sufficient. References are not required merely because they exist.

## Truth, authority and outcomes

- Creativity does not authorize publication, code changes, project-canon edits, paid APIs, connecting external systems, destructive operations or disclosure of private material. No silent relaxing of accepted constraints.
- Do not invent results, benchmark gains, source support, working tool capabilities, other-agent opinions or observed successful QA. Novelty is not usefulness or verified originality.
- Distinguish **concept hypothesis** from **measured improvement**. If a tool is inadequate for exact geometry/behavior, say so; choose an authorized more controllable production route rather than repeating a failing prompt.
- **Output contract:** if exploration was requested, give a *brief decision-ready concept outcome*, not a mandatory template. If production was requested, deliver the real artifact or precisely state the unmet production capability. Avoid unsolicited approval gates and speculative reports.

## Examples of owner selection

- “Invent two structurally different explanations for the same phenomenon; don't draft the article yet.” → Creative Reasoning may own the conceptual comparison; Drafting later owns the article.
- “The approved icon's proportions keep changing despite localized requests.” → Diagnose execution vs conceptual fixation; Icon Design keeps the icon output.
- “Find different technical ways around latency but preserve semantics and no paid services.” → Creative Reasoning can support Architecture Design; no invented performance figures.
- “Export the accepted icon at platform sizes.” → Icon Design only; **no** Creative Reasoning.
- “Correct the capitalization in this paragraph.” → Editing/Drafting only; **no** Creative Reasoning.
