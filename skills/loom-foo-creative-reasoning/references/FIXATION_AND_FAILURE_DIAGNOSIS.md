# Fixation recovery and causal failure diagnosis

**Load when:** a user reports repeated near-duplicates, an agent keeps proposing the same rejected conceptual approach, or the team is about to reset a direction after repeated failed attempts. Repetition is a *symptom*, not necessarily a creativity deficit.

## Establish failure type before generating

| Observed failure | Minimal intervention | Do not do |
| --- | --- | --- |
| **CONCEPT**: same rejected working principle appears in different disguises | Explicitly reject that principle; pivot to another functional decomposition or causal mechanism | Return the same design with changed color/material |
| **REPRESENTATION**: chosen depiction cannot express required form/behavior clearly | Try another representation while preserving accepted semantics and output requirements | Treat the medium swap as permission to change product behavior |
| **TOOL**: generation/editor cannot reliably preserve exact geometry/local details | Keep approved source; switch to a controllable edit method, precise mask, vector or code where available | Repeatedly rerender an entire accepted artifact and call drift “creativity” |
| **CONSTRAINT RETENTION**: model or handoff forgets a protected requirement | Recover constraints/approved base and repair task framing or handoff | Propose new concepts without restoring invariants |
| **EVALUATION**: nobody checks at actual size/state or against the right acceptance criterion | Inspect the actual output in context and compare with user feedback | Claim improvement from prompt wording alone |
| **TRUE CONFLICT**: accepted constraints are mutually incompatible | Surface exact conflict and smallest possible owner decision | Silently relax one constraint |

1. Reconstruct *what is approved* and *what is rejected*. Do not change a large approved master to repair only the small-scale version.
2. Compare recent attempts by the repeated **principle**, not by cosmetic differences.
3. Identify failure type(s) with observed evidence. Mixed cases are possible; address the most decisive cause first.
4. Preserve the last verified-good artifact or specification. For execution/tool failures, return to the responsible production skill with a localized fix.
5. Only for genuine concept failure: mark a do-not-repeat principle and introduce a structurally different option. Test against the original failure and invariants.
6. If the required tool/source cannot be accessed, say what cannot be checked; do not claim a repaired artifact or pass.

## Contrast examples

- Bad: accepted car-icon silhouette drifts, so alter the silhouette again to make rendering easier.
  Better: keep the accepted master, isolate a small-size legibility issue; use optical-size treatment, local geometry or a controllable production method.
- Bad: writing variations remain the same plot but with new adjectives.
  Better: change the narrative causal progression or viewpoint only if the user asked for narrative alternatives, preserving facts.
- Bad: pipeline latency persists, so propose a novel distributed service without timing evidence.
  Better: instrument the observed bottleneck; only then explore truly different interventions when a system-design choice remains.

## Exit

Correct diagnosis and a targeted next action can be a successful outcome even when no concept pivot is warranted. For a requested finished artifact, produce/repair it where possible. Stop after the failure is demonstrably addressed or identify the remaining observation needed.
