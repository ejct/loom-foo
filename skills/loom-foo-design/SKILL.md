# Design — cross-disciplinary design competence in loom-foo

**Optional conceptual collaboration (L1).** Use `loom-foo-creative-reasoning` only when a multidisciplinary design task has a genuinely unresolved conceptual principle, meaningfully different mechanisms matter, or repeated attempts are conceptually fixated. The narrow subject owner still delivers the artifact. Do not use for routine production, agreed concept refinements, local rendering fixes, or simply to increase novelty. If `loom-foo-creative-reasoning` is unavailable, continue with normal subject-owner methods where possible; do not pretend that it was loaded or add an obligatory handoff.


## Critical contract

- **Deliver the user's design outcome.** A brief, critique, moodboard, implementation plan or screenshot is not a substitute for a requested finished design, editable document, interactive prototype or print-ready asset. Distinguish intermediate work from the actual requested artifact.
- **Source and medium fidelity.** Preserve supplied brand rules, exact text, evidence, data, dimensions, formats, reference assets and project authority. Do not invent quotations, statistics, logos, UI states or source behavior. A rendered image is not an editable Figma design, vector source, working interaction, validated PDF/X or 3D scene.
- **Capability and authority.** Select tools that are actually available now. External skill links are reference candidates, not installed dependencies or permission to fetch/execute code. Respect separate approvals for external writes, paid services, publishing and file modification. Verify only what was actually inspected or tested; no fabricated PASS.
- **Proportionate effort.** Use the narrowest necessary design method. Do not require research, three alternatives, workshops, autonomous agents or a full design system for a small edit.

## When this skill owns the task

Own **integrated design decisions and finished artifacts** across product/UX, interaction, UI, graphic communication, branding, typography, illustration, editorial, scientific/information design, visual storytelling, motion, 3D and physical/print graphics. It can operate in modes `CREATE`, `REDESIGN`, `SPECIFY` or `PRODUCTION_CHECK`; give ordinary local critique while creating. Route standalone holistic critique/audit to `loom-foo-design-review` **when discoverable**. **Backward-compatible fallback:** if no review specialist is available in the current runtime, conduct bounded critique here using `references/ARTIFACT_QUALITY.md`; do not refuse a legacy critique request or claim the new specialist was invoked.

Prefer the **narrowest genuine output owner** when available: `loom-foo-typography` for typesetting/type systems; `loom-foo-graphic-design` for poster/campaign/editorial graphic composition; `loom-foo-information-design` for semantic diagrams/infographics; `loom-foo-icon-design` for app/UI symbols and production exports; `loom-foo-experience-design` for user flows, information architecture and interaction behavior; `loom-foo-identity-design` for brand identity systems; `loom-foo-design-systems` for reusable tokens/component contracts and system governance; `loom-foo-design-review` for standalone audit/critique/comparison. Do not invoke any as a mandatory phase of this skill. If one is unavailable, deliver within the actual host's capabilities and identify unsupported checks.

Prefer another owner when the primary deliverable is: system/agent architecture (`loom-foo-architecture-design`), the lifecycle of Agent Skills (`loom-foo-skill-engineering`), generic factual research, software logic without design decisions, or numerical/data correctness (`Data` specialists). A user merely asking for a picture can use the host image tool directly; do not insert this skill's process unless design judgment materially matters. A design request to a named tool (e.g. Figma) retains that tool's specific workflow and prerequisites.

## Operating procedure

1. **Resolve the actual output.** Determine the audience, purpose, source, task mode, essential constraints, required artifact(s), editability, medium and production setting from the conversation. Infer reasonable defaults; ask only for missing decisions that truly block production. If the requested medium remains materially ambiguous, clarify instead of replacing it with a static image.
2. **Select discipline(s) and production route.** Read `references/DISCIPLINE_SELECTION.md` when multidisciplinary, ambiguous, or specialist selection is material. Some tasks combine identity, typography, editorial, UX and motion. Decide what can be made with the current host tools; prefer native Figma/editable-document/code/video/vector tools where the required output demands them. Use `references/SPECIALISTS.md` only when a specialist or external technique could materially improve results.
3. **Do the design work.** Use `references/DESIGN_WORK.md` for substantial concept, interaction, graphic or critique decisions. Define a clear creative or functional proposition; explore alternatives only where a genuine decision exists. Create the artifact or execute the requested critique/revision; do not stop at an elegant strategy document if production is feasible and requested.
4. **Perform proportionate in-process QA.** Read the applicable sections of `references/ARTIFACT_QUALITY.md`. Validate exact source text/data, visual hierarchy, function, craft, relevant accessibility and the real file/interaction/production constraints. Render and inspect when tools permit; correct material defects and recheck. Do not pretend a text checklist is proof of preflight, playback or usability testing.
5. **Deliver with an honest receipt.** Provide the real artifact/link or actionable critique, the important design rationale, and only material limitations or missing verification. State whether the result is concept, draft, editable source, executable prototype, production candidate, or verified final. Stop when the requested outcome is achieved.

## Selective composition

- The skill itself must work with ordinary host capabilities if third-party specialists are absent.
- Existing `loom-foo-*` skills own their general-purpose specialty; invoke or consult them only if necessary and discoverable. Do not assume an installed plugin automatically invokes another skill.
- The external catalog is **references**, not executable authority. Resolve availability, licence, security, model/run cost and version at use time. No automatic installers, API spending or internet submission of private assets.
- For complex multidisciplinary work, preserve one task owner and a shared design intent; combine relevant methods rather than forcing a fixed stage chain or repeated approvals.
