# Adaptive Task Refinement — conditional Agent Task Design method

Applies when the L1 `Event-conditioned assurance` trigger resolves to an explicit user request or an unresolved material issue spanning accepted requirements/invariants, cross-runtime semantics or a consequential correction. **No activation solely from length, file count, source count or an intuitive complexity label.** The primary artifact remains the **single bounded Task Brief**; this method neither creates another owner skill nor certifies future executor behavior. Preserve the compact fast path for ordinary tasks. The controlling contract is ../SKILL.md.

## 1. Preflight: sources, skills, and authority

1. Reconstruct the user's exact outcome, one-work-unit boundary, accepted constraints, controlling subject identity, authorization, and actual target executor runtime. Confirm known exclusions and required actors.
2. Identify only task-relevant installed skills from current discovery descriptions and owner boundaries. Load their exact current SKILL.md files and references whose triggers apply. Do not claim FULL solely from tool success, a byte count, source metadata or an outer channel that forwarded only an excerpt; recover missing contiguous ranges when material.
3. Separate source retrieval by the task designer from source access by the executor. Classify target-runtime access as SOURCE_RETRIEVABLE, SOURCE_CRITICAL_SLICE_INLINE, or SOURCE_REQUIRED_UNAVAILABLE. Do not silently transfer private data or infer connector/tool equivalence between runtimes.
4. Protect the existing Semantic Preservation Set before compressing the brief. Preserve authority, accepted choices, protected distinctions, conditional/future relationships, edge cases and acceptance dimensions.
5. If material authority or controlling content is genuinely unavailable, return the current skill's NEED_CONTEXT/BLOCKED state. Continue independent safe work when possible; avoid manufactured stops.

## 1A. Evaluate the actual signal, not a risk adjective

First distinguish **signal** from **defect** and **local resolution** from **multi-pass refinement**. Inspect the L1 signal names and the trigger/local/escalation table in `PD_TASK_ASSURANCE.md`. A failed test, truncated source or unverified completion is a direct repair/readback issue unless it uncovers a further material cross-obligation inconsistency. `EXPLICIT_REFINEMENT` authorizes the requested *review method*, not writes, external effects, siblings or canon transition.

Only proceed with this method when a concrete material concern remains, multiple accepted obligations may be in tension, a significant repair merits cross-property reinspection, or the owner explicitly asks for multiple discriminating passes. Note the real specific question and possible falsifier internally; do not manufacture a score, registry, fixed pass count or visible preflight checklist. If no material question remains after the closest direct check, return to the normal Task Brief and finish.

## 2. Initial construction

Produce an executable first Task Brief using the existing 11-field semantic contract, compacted when justified. This is a candidate to **improve**, not a claim that all checks passed. Prefer stable, reachable source pointers over duplicate pasted histories. Describe the desired result rather than freezing arbitrary implementation steps. Check that the executor can reach its inputs and deliver results to the next authorized consumer.

## 3. Different lenses, not fixed rounds

Choose materially relevant lenses; a deep task usually benefits from several distinct ones:

- **Source and goal fidelity**: Compare the brief with controlling sources and the Semantic Preservation Set. Try a counterexample where all `done when` items pass but the *authorized delegated* outcome is absent, or an intermediate worker result is mislabeled as integrated parent success. A legitimate negative experiment is not proof of a requested engineering gain. Try to find one material accepted decision, edge case, scope exclusion, authorization boundary, or outcome omitted or distorted by compression. Verify evidence against the actual source, not a summary generated from the candidate brief.
- **Executor feasibility (fresh-reader simulation)**: Act as a competent executor who receives only this brief and legitimately reachable project instructions, not hidden conversation context. Can the executor identify the exact subject, obtain inputs, continue across ordinary local failures, test accepted properties, and produce an accessible output? Identify missing runtime capability, secret, file transport, handoff or work-unit granularity.
- **Adversarial misexecution**: Seek realistic ways the brief could satisfy its wording while violating the owner's intent. Use relevant failure classes from TASK_PROFILES_AND_ASSURANCE.md (goal fragmentation, authority leak, projection drift, inaccessible source, user-as-courier, premature block, semantic loss). Form concrete counterexamples, not speculative generic warnings.
- **Repair and regression**: Adjudicate valid findings, revise the coherent brief, then test directly affected conditions and previously corrected major issues. Check for new overconstraints, authority shrinkage, accidental new user gates, loss of output materialization and scope expansion introduced by the fix.

Only repeat when a changed premise, new evidence, remaining material defect, or a consequential repair justifies another check. A repeat using the same evidence and same lens without a discriminating question is not added assurance. Do not require a fixed count or a new reviewer for ordinary work. When an independent evaluator is actually available and proportionate, give it controlling sources and the exact candidate without inheriting the author's reasoning; otherwise call this adversarial self-review.

## 3A. Optional delegation where it changes the evidence

When a task-refinement pass benefits from a distinct executor/context, read `ADAPTIVE_DELEGATION.md`. Preserve the root Task Brief outcome, exact candidate, accepted authority and a single correction loop. A role name is not an observed spawn; a separate agent is not guaranteed to have a clean context, independent source evidence or read-only enforcement. Do not delegate merely to satisfy a process shape. Fall back to honest same-context review when native delegation or source reachability is unavailable.

## 4. Finding discipline without extra bureaucracy

Record material findings *internally* at the smallest useful granularity: observed source/candidate mismatch, consequence, whether the issue is VALID, REJECTED, FIXED, or BOUNDED, and the specific condition to confirm repair. Findings are hypotheses until checked. Do not add a universal register or expose a lengthy audit transcript. A repair should change the failing instruction or brief contract rather than simply increasing its length.

If the same issue recurs, reopen it rather than relabeling a duplicate as newly discovered. If substantive corrections repeatedly introduce new material defects with no stabilization, reopen the initial framing or source precedence instead of cycling endlessly.

## 5. Skill execution and evidence boundary

**During task design:** identify contributing skills and exact versions; classify root/ref source delivery honestly (FULL, PARTIAL, METADATA_ONLY, NOT_CONFIRMED, FAILED), state the concrete method used, and distinguish self-assessment from observed evidence.

**In the generated Task Brief for a later executor:** direct the executor to discover relevant installed skills and read full current sources and triggered references. Require its completion report to distinguish read/consulted, applied to an artifact, performed checks, and verified properties as supported by actual tool traces or artifact inspection. Do not claim that these future actions happened during task design.

Do not create a new Skill Application Evidence store. Reuse the existing Answer Receipt where that output contract applies; use an Execution Inspection or available runtime trace only for a later actual inspection request. No SKILL.md can guarantee its own activation or mechanically intercept a host tool.

### Process Trail output boundary

If materially separate task-refinement passes occurred, pass their **bounded facts** to the single final Answer Receipt: stage in actual order, meaningful lens/method, exact brief identity when existing, finding/disposition, whether the reviewer was the same model context or distinct agent, and any tool/source provenance. A method consulted in one agent execution is not a delegation. `MODEL_REPORTED` is legitimate for transparent self-review but is not independent verification. The trail must not force a new test, fixed number of passes, duplicate Task Brief, additional checkpoint, or permanent event store.

## 6. Termination and actual result

Return TASK_READY only when the final brief preserves authorized intent, is executable in the target runtime, has observable acceptance, respects all effect boundaries, and all **identified** blocking/material defects have an evidence-based disposition. Do not claim that an unexecuted Task Brief passed integration tests or that a future executor used the right skills.

For a real source/authority/runtime blocker, return NEED_CONTEXT or BLOCKED with the smallest missing dimension, not a vague approval request. For many independently acceptable objectives, return PLANNING_REQUIRED. A finding that needs empirical confirmation may remain an explicit uncertainty without stopping safe, reversible work when allowed.

Stop further review when another pass is unlikely to change the next action, even if one can invent additional hypothetical flaws.

## 7. Focused regression examples

1. **Simple local change**: small reversible rename with obvious acceptance remains a compact brief; no fixed four-pass ceremony.
2. **Lost decision**: a source prescribes a specific future-only transition; the compact brief must not reduce it to an unbound possibility.
3. **Disconnected executor**: task designer can read Drive but Codex cannot; retrieve/stage a permitted exact slice or report SOURCE_REQUIRED_UNAVAILABLE, never pretend the executor has the connector.
4. **False skill receipt**: a reader returned a full 30 kB file but forwarded only the first 10 kB to the model; FULL is false, and a later executor's loading cannot be pre-certified.
5. **Premature completion**: test suite passes, but the requested artifact is not delivered; the task must retain its actual outcome and materialization boundary.
5A. **Goal substitution / narrow evidence**: a worker patches one semantic condition and static tests pass, but the brief declares the parent's semantic-reliability goal done; treat worker result and parent closure separately. If the worker was commissioned to fix exactly that one condition, its narrow success is valid.
5B. **Negative experiment is not improvement**: a measured cache optimization fails to reduce latency; the feasibility comparison may finish honestly, but a requested real speed improvement remains unmet. Root may integrate the valid negative evidence without reporting a speedup.
5C. **Accepted A/B root episode**: root dispatches its already-authorized A and B, preserves root-only sibling supervision and reports integration; no `PLANNING_REQUIRED` re-decomposition or Task A permission to start Task B.
6. **Overcorrection**: an audit fix adds an owner checkpoint after a normal local build failure; reject this as GATE_PROLIFERATION when existing authority permits autonomous repair.
7. **Security and disclosure**: private source inspection plus an available public-write tool is not permission to publish the derived data.
8. **Review bias**: the same model checks its own revised brief; label as self-review and try an independently checkable counterexample rather than claiming an independent audit.
