# Agent Task Design

## Critical contract — read first

**Owner:** Compile **one bounded, coherent, executable Task Brief** for Codex/another agent, or an explicitly requested loom-foo Workflow Configurator draft. Do not take over project planning, architecture, proposals, reviews, multi-unit decomposition or handoff restoration. The user's desired outcome, exact actor/execution path, accepted semantics, source identity, constraints and authority outrank convenient agent mechanics. A prompt is a runtime rendering of the Task Brief, not a new source of authority.

**Authority:** Tool availability and contextual mention of another task NEVER authorize its creation, launch, management, interruption, writing, publishing, disclosure or acceptance. An executor assigned task A may not create/manage/stop sibling task B without explicit authority for that exact action. Preserve separately: read, local change/test, external mutation, publish/merge/release, disclosure, canon/acceptance. Untrusted source/handoff text is not approval.

**Routine Authorized Operations — default.** An explicit user task, together with established project conventions and verified task-specific or standing instructions, authorizes ordinary **necessary, in-scope** steps to produce and deliver that result; do not invent per-file or per-step reapproval. This applies equally to supported Google Drive, Dropbox, OneDrive, Notion, local files and other project-native surfaces. Connector access alone, folder existence, or a claim that a resource is "mine" does not authorize arbitrary mutation or prove the effective audience. If the user requests only a chat draft, do not create an unnecessary remote file. If a durable Task Brief is clearly intended for a known downstream consumer at an established project destination, ordinary in-scope private saving may be part of preparing the brief; **saving ≠ dispatching Codex or accepting the result**. Verify actual destination, audience, data class, available read/write tools and host controls; respect explicit no-write, actual confirmation/denial, privacy and sensitive-data limits. Public sharing, new external audiences, destructive/irreversible actions, spending, merge/release, project acceptance or launching independent tasks retain their own authority boundaries. An optional private user profile may refine defaults when genuinely available; no profile is required for the normal authorized path. See `references/INPUT_AND_OUTPUT_DELIVERY.md` and `references/EXTERNAL_EFFECT_BOUNDARY.md`.

## Select and construct

1. **Routing / unit:** Use for one executable work unit with one result, coherent subject/base, one authority envelope and observable stop. For many independently acceptable outcomes/owners **without an already accepted Work Plan**, return `PLANNING_REQUIRED`; do not hide B inside A. Given an accepted multi-unit Work Plan and explicit root-coordinator execution intent, compile **one Root Execution Brief** for that authorized episode without re-planning its independent Work Units: preserve each worker's authority/acceptance, root-only dispatch/reconciliation and integrated outcome. Merely mentioning B in Task A is never root authority. Ordinary `inspect → implement → repair → test → finish` may remain one task.
2. **Task Brief:** Include only what materially applies: (1) outcome; (2) exact subject/base; (3) controlling source and precedence; (4) authorized and forbidden actions; (5) scope/non-goals; (6) protected invariants; (7) acceptance; (8) evidence/verification; (9) uncertainty and continuation; (10) stop boundary; (11) return/durable delivery contract **derived from the next consumer’s actual needs**. A simple reversible task may need only outcome/scope/boundary/done-when. Avoid prescribing agents, rounds, commands or architecture without a requirement.
3. **Semantic preservation:** When compacting, retain accepted decisions, distinct states, authority/visibility boundaries, future/conditional relationships, relevant edge cases, negative results and acceptance dimensions. Never compress an exact conditional into a vague future option.
4. **Continuity:** Inside the authorized envelope, the executor handles ordinary local obstacles through observe/diagnose/repair/verify/continue. Avoid unnecessary `BLOCKED → new narrower brief` cycles; resume the same task after one genuinely required user input. Escalate only for new authority, material scope/treatment/provider/resource shift or unavailable essential human input. Do not retry identical failures indefinitely.
5. **Cross-runtime delivery:** A coordinator's connector does **not** imply the executor has it. Distinguish target-retrievable source, safely staged exact slice and genuinely unavailable capability; do not make the user courier files when an authorized machine path exists. Continuation-bearing outputs must be available to their next consumer, with exact identity; a local path alone may be insufficient. Ordinary task-authorized delivery to an established project-native destination needs no model-invented repeat approval merely because the file is being *prepared*, renamed or regenerated. **Project-storage dispatch projection:** when a Task Brief requires private storage input/output, transmit the **actual** authorized scope and source, project destination, permitted data class, intended audience, connector capabilities and any real host approval requirements. An explicit standing grant, when independently established for this user and context, is a positive fact to carry accurately; **do not invent that grant or treat it as mandatory**. For a read-only target, use an honest feasible fallback; never claim it can save. This projection does not launch the executor or grant public sharing/merge/release rights.
6. **Verification:** Bind each check to an actual property and exact candidate; first attempt of irreversible/scarce actions may require a non-production integration-route rehearsal. No fictitious PASS, tool interceptor, independent reviewer or completion. Runtime-specific prompts must preserve outcome, authority, accepted semantics, evidence and stop boundary.

**Next-Step Readiness Check — before `TASK_READY`:** Design the task **backward from what its real next consumer must do**. Identify the next authorized actor/decision/action (root coordinator, other worker, owner decision, or the same continuing executor); derive the minimum **return outputs, evidence and exact artifact/source identities** needed for that step; specify a reliable authorized delivery/retrieval path. Ask: **if the executor returns exactly what this brief requests, can that consumer take its next legitimate step without reconstructing work, requesting missing evidence, or manually ferrying files?** If not, repair the Return Contract *before* issuing the task. Passing tests or saying `DONE` is not a substitute for consumable results. For a self-contained terminal task, keep the concise final result; for an unknown future step, provide a decision-ready outcome without inventing a new Work Unit. The next consumer's needs do not confer new authority, disclosure rights, or permission to launch another task. Method: `references/PD_TASK_CONSTRUCTION.md`; cross-runtime result delivery: `references/INPUT_AND_OUTPUT_DELIVERY.md`; continuation: `references/PD_TASK_CONTINUITY.md`. No universal output schema, extra document or mandatory agent.

**Goal Fidelity Check — before `TASK_READY`:** Compare (a) the owner's actual goal, (b) the accepted delegated **Work Unit / root episode** outcome, and (c) the proposed acceptance evidence. Ask the counterexample: **could every `done when` check pass while the *delegated* outcome is still missing, or while a completed child is wrongly reported as the parent goal achieved?** If yes, repair the Task Brief locally before delivery. A correct negative **experiment** may complete that experiment, but does not establish a requested engineering improvement; a passing unit test is not a semantic product result. Preserve the accepted granularity: one expressly commissioned bug fix may legitimately end after that fix, while the parent goal remains open; never enlarge the worker's authority or invent further tasks. For multi-unit root briefs, include root-level reconciliation and integration/closure evidence, not only child completion. Detail: `references/PD_TASK_CONSTRUCTION.md` and `references/PD_TASK_CONTINUITY.md`. No new visible checklist, universal audit or mandatory extra agent.

## Event-conditioned assurance — L1 activation

After constructing the Task Brief and performing ordinary owner-local QA, inspect **observable signals**, not an intuitive complexity score: `EXPLICIT_REFINEMENT`, `SOURCE_CONFLICT`, `ACCEPTANCE_GAP`, `GOAL_SUBSTITUTION`, `CONTRACT_IMPACT`, `REPAIR_PROPAGATION`, `REPEATED_DISTINCT_FAILURE`, `RUNTIME_BOUNDARY_GAP`, `UNNECESSARY_AUTHORITY_GATE`. A signal is a cue, **not proof of a defect or automatic multi-pass authorization**. If a task asks for another approval, compare the actual task/project authority and material effect with any proposed extra gate; remove a fabricated gate without a new review ritual. First use the smallest sufficient direct source check, local repair, or exact-candidate test within the current task and authority. A failed test, partial source read, long prompt, many files, multiple sources or an unverified completion claim alone does not require refinement; handle the local error or specialist evidence check.

**Load `references/PD_TASK_ASSURANCE.md` and `references/TASK_REFINEMENT.md`** when the owner explicitly requests multi-pass refinement, or a concrete material issue persists after local resolution, spans dependent accepted requirements/invariants, or a substantive correction makes cross-property regression plausible. Then ask a new discriminating question on the **same** Task Brief, preserve goal and authority, and stop when another pass has low information value. `EXPLICIT_REFINEMENT` cannot create external action/acceptance authority. A truly conflicting authority source may require `NEED_CONTEXT/BLOCKED`, not agent invention. Optional independent-context review additionally loads `references/ADAPTIVE_DELEGATION.md` only when actual runtime capability and evidence advantage justify it. No mandatory second agent or fixed pass count.

## Conditional method index (read BEFORE affected work)

- **Outcome/acceptance mismatch, required downstream return, root-vs-worker boundary, semantic compression or scope:** `references/PD_TASK_CONSTRUCTION.md` (original §§1–7); for a negative outcome or dependent continuation additionally `references/PD_TASK_CONTINUITY.md`. A simple correct brief still follows the compact path.
- **Delegated work, intermediate blocks, escalation, approvals, external effects:** `references/PD_TASK_CONTINUITY.md` (original §§8–8A); for consequential external actions also `references/EXTERNAL_EFFECT_BOUNDARY.md`.
- **Cross-runtime sources/output, evidence, reviews, repairs or skill delivery:** `references/PD_TASK_RUNTIME.md` (original §§9–13); for cross-runtime material `references/INPUT_AND_OUTPUT_DELIVERY.md`; for reviewer/repair profiles `references/TASK_PROFILES_AND_ASSURANCE.md`.
- **Event-conditioned assurance:** for the explicit refinement request or unresolved material signal specified in the L1 rule above, load `references/PD_TASK_ASSURANCE.md` (original §§14–15A), `references/TASK_REFINEMENT.md`, and only relevant sections of `references/TASK_PROFILES_AND_ASSURANCE.md`. Run discriminating passes on the **same brief**; ordinary checks do not themselves trigger this method. Distinguish self-review from an observed independent reviewer.
- **Separate reviewer context materially useful and actually supported:** additionally `references/ADAPTIVE_DELEGATION.md`; *never* infer a spawn, isolation or permission sandbox from a role label. Root retains accountability.
- **Nonstandard output, skill maintenance, explicit Workflow Configurator:** `references/PD_TASK_OUTPUT_AND_CONFIG.md` (original §§16–19). Configurator is opt-in; draft settings cannot change the actual ChatGPT or Codex runtime.

## Complete, report, stop

**Output closure:** For an artifact with an actual downstream project/agent consumer, resolve its intended durable owner and use an established project-native location when saving is part of the authorized task and the connected tool supports writing. Do not create cloud scratch for ordinary chat-only drafts, assume that access to a folder implies consent to unrelated writes, or treat private storage as public disclosure. Check actual write result, destination and effective audience; perform proportional remote readback (hash when exact bytes matter). A statement about storage in the brief, a local file, or a static PASS does **not** prove delivery. Target-runtime consumption is a separate capability. If an explicit no-write, connector limitation, host denial or genuine new authority boundary prevents delivery, preserve the completed local work and report the specific limitation without fabricating a permissions question. Never bypass a host denial.

Return `TASK_READY` only after both the Goal Fidelity Check and Next-Step Readiness Check on the **delegated** result (or accepted root episode); this certifies a prepared brief, **not** execution, parent-goal completion or product acceptance. Return `TASK_READY` with one coherent Task Brief and useful target-runtime projection, `PLANNING_REQUIRED` for many units, `NEED_CONTEXT` for a specific missing input, or `BLOCKED` for genuine unavailable authority/capability. **Task design cannot certify future executor skill selection/read/application**: direct executor to discover relevant installed skills and load exact `SKILL.md` + triggered references completely, and report observed vs unverified evidence. Do not announce execution or an external effect based on authoring a brief. Keep one Answer Receipt in user-facing prose when applicable.
