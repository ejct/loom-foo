# Problem Understanding

## Critical contract — read first

- **Goal fidelity:** Preserve the owner's real result, required actors, source identity, constraints and scope. Do not treat an intermediate result as completion unless it is the exact outcome the user requested and meets its acceptance criteria.
- **Authority and verification:** Tool access cannot grant new action authority. Keep evidence proportional to the actual claim and honor the scope, refusal, resource and acceptance boundaries detailed below. Load conditional references when their trigger applies.

Turn a materially ambiguous situation into a fit-for-purpose **Understanding Model** without absorbing downstream artifact ownership.

Core boundary:

`materially ambiguous situation -> Understanding Model -> STOP or stronger owner`

This skill owns **pre-owner ambiguity**, not generic critical thinking.

## L1 — ordinary execution and L2 selection

Reconstruct the exact ambiguity and distinguish facts, interpretations and unresolved definitions; produce a compact Understanding Model or route immediately when the owner is already clear. Avoid solving an adjacent architecture, research or proposal artifact under the guise of understanding.

**Conditional method index (read the selected file before its detailed method is needed):**

- **Conflicting hypotheses, material alternatives or low-cost discriminating evidence would change the problem framing** → `references/PD_PROBLEM_CHALLENGE.md` (source H2 sections 6,7,8).

**No-trigger:** a short, resolved ordinary case does not require all detailed references merely because this skill was selected. Existing specialist references linked inside these materials remain conditional on their original situations. A moved section does not grant new permissions or replace the owning L1 safeguards.

## 1. Routing gate

Use when all material conditions hold:

1. the situation/question is consequential enough that framing affects the result or next action;
2. the subject, problem, frame, explanation, distinctions, or controlling uncertainty is materially unclear;
3. that ambiguity blocks or would materially distort a stronger primary-output owner;
4. the uncertainty cannot be closed more cheaply by a direct factual check or obvious bounded probe.

Do not use as primary owner when:

- the requested artifact is already explicit and sufficiently bounded;
- the question is a normal factual/concept explanation with a stable subject;
- a direct lookup, source check, deterministic test, or small reversible experiment is the highest-information next step;
- an artifact-specific reviewer already owns the object.

Typical direct routes:

- bounded project proposal -> `loom-foo-proposal-refinement`;
- frozen/new architecture -> `loom-foo-architecture-review` / `loom-foo-architecture-design`;
- bounded empirical uncertainty -> `loom-foo-research-design`;
- existing evidence body -> `loom-foo-evidence-review`;
- bounded alternatives/action synthesis -> `loom-foo-decision-reconciliation`;
- bounded implementation/change -> relevant change owner.

If the apparent downstream artifact is explicit but its framing is too unstable for that owner to proceed defensibly, use problem-understanding only for the blocking ambiguity, then hand off.

## 2. Establish the understanding target

Identify compactly:

- what the user is trying to understand;
- why the distinction matters;
- scope and exclusions;
- current observations/constraints;
- what is unclear enough to affect the answer or next owner.

Do not turn this into a questionnaire when a bounded working model can be formed from available context.

## 3. Reconstruct before evaluating

Recover the smallest relevant current situation.

When material, distinguish:

- observed / directly established;
- accepted authority or constraint;
- inferred;
- assumed;
- unknown.

Do not treat a remembered interpretation, prior proposal, or generated summary as stronger authority than the project source it describes.

## 4. Separate conflated concepts

Search for distinctions whose collapse could be causing the ambiguity.

Examples:

- user-facing flow vs backstage process;
- evidence vs interpretation;
- correlation vs causal attribution;
- current state vs desired state;
- product value vs implementation structure;
- factual uncertainty vs value disagreement;
- architecture question vs empirical question;
- reversible experiment vs analysis problem.

Create only distinctions that change understanding or routing.

## 8. Revise the working model

After relevant distinctions, alternatives, and checks:

- retain the current model if it survives;
- revise only what findings justify;
- keep unresolved alternatives visible when evidence does not discriminate them;
- identify any controlling crux that remains.

Do not force a novel conclusion.

## 9. Produce the Understanding Model

Read `references/UNDERSTANDING_MODEL_CONTRACT.md`.

The output should be as small as the task allows.

Potential elements, only when material:

- subject/question;
- relevant situation;
- established observations/constraints;
- interpretations and assumptions;
- important distinctions;
- plausible alternative frames/explanations;
- contradictions/tensions;
- unresolved unknowns;
- controlling cruxes;
- best current understanding;
- what would change it;
- stop or next owner.

Persistence is optional. The Understanding Model may be inline, conversational, embedded in a handoff, or durable when continuation/reuse justifies it.

## 10. Stop and route

Stop when one of these holds:

### `UNDERSTANDING_READY`
The working model is fit for the user's current purpose and no downstream artifact is required.

### `ROUTE_TO_OWNER`
A stronger primary-output owner is now clear and can proceed without reopening the same ambiguity.

### `DIRECT_VERIFICATION`
A bounded factual/source/tool check is the highest-information next step.

### `RESEARCH_REQUIRED`
A material uncertainty now has a sufficiently clear claim/alternatives to route to `loom-foo-research-design`.

### `NEED_CONTEXT`
A material ambiguity cannot be resolved responsibly from available context and no bounded assumption permits useful progress.

### `NO_MATERIAL_AMBIGUITY`
The task is already sufficiently framed; do not add a problem-understanding layer.

## 11. Proportionality

Use the cheapest reasoning that can change the result.

Small case:
`reconstruct -> distinguish -> stop`

Larger case:
`reconstruct -> distinguish -> alternatives -> targeted challenge/evidence -> revise -> crux -> route`

Do not require matrices, scores, named methods, durable documents, or multiple passes by default.

Read `references/ROUTING_AND_PROPORTIONALITY.md` for edge cases.

## 12. Authority and side effects

This skill authorizes understanding work only.

It does not by itself authorize:

- accepting a project decision;
- changing canonical documentation;
- modifying code/configuration;
- publishing or sharing information externally;
- executing an irreversible action.

Downstream authority remains with the relevant project/user transition.

## 13. Final checks

Before returning:

- the ambiguity was material enough to justify activation;
- a stronger existing owner was not unnecessarily displaced;
- fact/inference/assumption are not silently collapsed where the distinction matters;
- missing alternatives were considered when material;
- external verification was preferred over introspective certainty when cheap;
- the output is smaller than the ambiguity it resolves;
- unresolved cruxes are explicit;
- stopping/routing is clear;
- no mandatory self-critique or artifact ceremony was introduced.
