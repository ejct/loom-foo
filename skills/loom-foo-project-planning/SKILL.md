# Project Planning

## Critical contract — read first

- **Goal fidelity:** Never turn proof, audits or infrastructure into substitutes for the first useful project result. Preserve the owner's real result, required actors, source identity, constraints and scope. Do not treat an intermediate result as completion unless it is the exact outcome the user requested and meets its acceptance criteria.
- **Authority and verification:** Tool access cannot grant new action authority. Keep evidence proportional to the actual claim and honor the scope, refusal, resource and acceptance boundaries detailed below. Load conditional references when their trigger applies.

Convert an authorized project objective and its actual current state into an **adaptive Project Route Plan**: a defensible route to the intended outcome, with the smallest useful set of milestones, dependencies, next moves, and conditions for change.

Core boundary:

`project outcome + actual state + material constraints -> route choice and adaptive plan -> downstream work owners`.

**Own route selection and revision, not detailed work breakdown or execution.** The primary output is a Project Route Plan, distinct from the Work Plan / Work Unit Set owned by `loom-foo-work-decomposition`.

## L1 — ordinary execution and L2 selection

Use Project Planning only when choosing or materially revising a project route. Restore actual owner outcome, state, resources and accepted constraints; select the smallest feasible route, next useful outcome checkpoint and actual replan trigger. Do not turn already authorized execution into a separate planning approval. A route plan never accepts the owner's strategy itself.

## 2. Establish a minimal planning frame

Identify, using current authorized project sources when available:

- **Owner outcome:** observable capability or project result, and why it matters; preserve what the owner actually wants.
- **Baseline:** what is completed, underway, blocked, abandoned, or already attempted; exact current artifact or release when relevant.
- **Authority:** accepted decisions, hard constraints, permissions, non-goals and external action limits.
- **Resources:** time/cost/capacity constraints only if they affect feasible routes; never invent budgets or deadlines.
- **Uncertainty:** only unknowns that could alter route choice, correctness, risk or near-term actions.

Keep **VERIFIED / ACCEPTED / INFERRED / ASSUMED / UNKNOWN** meaningfully distinct. Current controlling project artifacts outrank old plans, old conversations and broad contextual summaries. Honor recorded negative results; don't send work back to already exhausted sources without new grounds. Consult only sources that can change the route; do not re-research the entire project. For cross-project knowledge, use a bounded authorized knowledge/context lookup only when it could materially alter the route; do not perform knowledge intake or documentation writes as a planning side effect.

Do not require a clarification when a bounded reversible working assumption is enough to plan. State material assumptions and continue. If the requested outcome itself is genuinely missing, provide a best-effort provisional route with the one exact question that changes it, rather than inventing authorization.

## 3. Decide which planning resolution is warranted

- **Compact:** 1–3 coherent moves, small reversible goal, no independent gates. Produce a brief direct answer; avoid a document.
- **Standard:** multiple stages or meaningful trade-offs; include a chosen route, key milestones, blockers and immediate next moves.
- **Consequential:** costly, risky, multi-owner, long-running or dependent on significant decisions; add competing routes, failure modes, integration and explicit replanning triggers. Read `references/ROUTE_PLAN_CONTRACT.md`.

A detailed plan is an optional tool, not evidence of quality. Do not automatically add milestones, stage counts, Gantt charts, scores, dates, estimates, research campaigns or user approvals.

**Planning horizon:** in uncertain work, detail only the near-horizon decision or executable checkpoint enough for a legitimate owner to act; represent more distant work as provisional outcomes, major constraints and revisiting conditions. Refine the future route from observed progress, not invented schedules. For a predictable, accepted, bounded project, a more detailed route may be appropriate without redundant replanning ceremony.

## 5. Build the smallest executable route

Express meaningful **outcome checkpoints**, not micro-steps. Include, when material:

1. Current starting point and target completion state.
2. Route and the rationale for selecting it.
3. Milestones that each change the project's usable state or remove a genuine uncertainty/dependency.
4. Only real prerequisites, parallelizable branches, integration points and authority gates.
5. The **next concrete action or workstream** that can begin under existing authority; give a clear default priority.
6. What will count as done, and what new evidence, failure or change will trigger replanning.

Check **first useful outcome** against planned activity: a research exercise, meeting or document is a milestone only when it removes a genuine dependency/uncertainty or produces needed usable value. The current horizon should be executable; future horizons can remain coarse. Assign no artificial dates, owner commitments or acceptance transitions.

Check whether accepted work is already ready for `loom-foo-work-decomposition`. If so, hand the accepted scope to that owner instead of duplicating its Work Unit Set. If a specialized artifact is the next milestone, name the right owner; do not covertly create architecture/spec/research decisions inside the route plan. A research item is a *gate* only if its answer is needed for an actual imminent decision or required integrity/safety boundary. Open questions are not automatically work units.

A project's route can include authorized sequential execution in the same delegated episode. **A planning result is not an automatic stop boundary for a user-authorized execution request.** Keep executing through ordinary observe/repair/verify/continue steps within the established authority, rather than demanding another user turn, a new Task Brief, or a fresh plan. Equally, do not infer approval to spend, contact third parties, mutate shared data, merge, deploy, publish or accept decisions from permission to produce a plan.

## 8. Final checks

Before finishing, verify:

- This was genuinely project-level route planning, not a sibling artifact or a replacement for requested execution.
- The selected route preserves owner goal and constraints.
- Feasibility was checked; no feasible route was invented, and any fallback is labeled honestly.
- Near-horizon detail and far-horizon uncertainty are proportionate; checkpoints represent usable outcomes or genuine gates.
- Stale/negative evidence and accepted work are not rediscovered.
- Next action is possible; real blocks and external permission gates are visible.
- Unnecessary proof phases, duplicate units, fabricated deadlines and false precision are absent.
- Trigger for **continue, replan, pause or finish** is usable.
- Planning is not described as execution, publication, approval or validated performance.

For a standalone planning request, stop once the route is sufficient for the next decision/execution owner. For an already authorized execution request, return control to the executor and continue the same delegated outcome without an artificial user gate. Do not convert skill use into a recurring management process without a separate request.
