## 6. Replan from a concrete delta

When a prior plan exists:

- Recover the latest accepted route and exact current state; distinguish proposals from accepted changes.
- Identify what changed: evidence, completed work, failed attempt, blocked prerequisite, resources, owner priority or external environment.
- Retain valid milestones, accepted decisions and negative knowledge; revise only the affected path or gates.
- Prefer continuing unaffected authorized work while one branch is blocked, when doing so preserves correctness.
- Mark **continue / switch / pause / stop**, with the reason and the immediate next move.

Do not restart discovery, re-open settled choices, turn ordinary tool failures into a new research project or claim that replanning has changed project authority. If the original target is no longer feasible, name the constraint and propose the smallest honest scope/route decision. A partial completion, routine failure or intermediate report does not itself authorize changing the terminal outcome.
## 7. Produce an appropriately sized Project Route Plan

Default to concise, actionable prose. For consequential plans, consult `references/ROUTE_PLAN_CONTRACT.md`. Include only fields that improve decisions or continuation:

- **Target and baseline** (with evidence/assumption boundaries where relevant).
- **Recommended route and rejected live alternative** (short reason).
- **Outcome checkpoints / critical dependencies / planning horizon** (detail near-term work; keep distant uncertain work coarse).
- **First action, executor class and acceptance boundary** (no full Task Brief).
- **Replan triggers, terminal condition and real owner decisions**.

A plan is **PROPOSED** unless its core route is already authorized. Explicit approval or controlling project authority is needed to mark a material new strategy as **ACCEPTED**. Output can stay in chat for an ephemeral answer; ordinary task-authorized project-native saving/editing of a durable project plan in its established destination is not a new approval gate or adoption. A private user grant may refine behavior when available, but does not define the universal default. A canonical project-state change, public release or unrelated external action remains a separate transition. Version/date/provenance matter for substantial durable plans, not quick advice.
