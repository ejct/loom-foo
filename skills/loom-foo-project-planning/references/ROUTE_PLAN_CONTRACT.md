# Project Route Plan — optional consequential-case contract

This file is a **shape guide**, not a mandatory document template. The `SKILL.md` owns routing and planning decisions.

## What a route plan is

A route is a selection of **how a project reaches the owner outcome from the verified baseline**, with meaningful checkpoints and adaptation policy. It differs from:
- a Proposal: justification of which product/change to pursue;
- an Architecture: structural design and trade-offs;
- a Work Plan: accepted work decomposed into independently acceptable units;
- a Task Brief: bounded agent execution contract;
- an Evidence Plan: method for resolving an empirical question;
- a calendar/project tracker: assignments, resource slots and schedules;
- skill engineering: choosing reusable knowledge delivery mechanisms and evolving a skill;
- a Decision Surface: reconciling already-bounded alternatives/evidence without inventing a broader project route;
- execution continuation: carrying an authorized outcome through normal inspect/repair/retry/verify steps.

## Useful fields (select only material ones)

| Field | Answer sought |
| --- | --- |
| Goal | What observable result is wanted and which adjacent goals are excluded? |
| Baseline | What state and prior failed/completed attempts can actually be verified? |
| Constraints | What fixed decisions, resources, permissions, non-goals control the route? |
| Route choice | Which credible strategy is preferred now, why, and against which real alternative? |
| Checkpoints | What interim states materially advance the owner outcome, rather than merely consuming effort? |
| Critical path | Which true dependencies/gates must precede later work? What can proceed independently? |
| Horizon | What can be concretely acted on now? Which distant stages are still provisional because uncertainty remains? |
| Feasibility | What decisive prerequisite or authority might make every proposed route infeasible? What limited fallback remains honestly available? |
| First move | What can start now, with what done-when boundary, without turning into an agent prompt? |
| Failure/fallback | What observation changes the route; what stays valid if one branch fails? |
| Finish | What demonstrates the owner outcome is achieved, or when continuation is unjustified? |
| Authority | Which decisions/actions are already authorized, proposed, or require a new approval? |

## Example: recovering a blocked source-led investigation

**Goal:** Obtain the primary record, or document an evidence-backed inability to reach it under the authorized constraints. **Baseline:** One official collection is identified, access is blocked; several other catalogs were already searched with recorded negative results. **Assumption:** A second authorized access channel may exist.

**Recommended route:** Preserve existing source coverage; verify the smallest alternative access path now; if successful inspect the exact full record and capture provenance; if unsuccessful pursue the next unsearched primary-source class. **Why:** Repeating catalog searches is low-value without new identifiers. **Critical gate:** Access permissions and actual availability, not a ceremonial new research phase. **First move:** Attempt the bounded permitted access path and record an explicit usable/blocked outcome. **Replan when:** A new identifier, genuinely different accessible source or refusal changes the search tree. **Finish:** Primary source captured with provenance or exhausted scoped routes documented, without inventing the missing fact.

This is a **synthetic planning illustration**, not evidence about any real family or repository.

## Example: minimal launch path

**Goal:** Ship a functioning pilot to first users under near-zero cash budget. **Baseline:** Flow concept exists; partner availability and checkout integration are uncertain. **Recommended route:** Confirm a narrowly scoped partner/offer and a working checkout route before polishing a broad platform. Run the simplest usable pilot, then revise only the components constrained by actual user behavior. **First move:** Specify the smallest partner-dependent pilot and identify the permission/offer that controls feasibility. **Replan when:** The partner declines or the checkout path proves infeasible. **Not a gate by default:** Competitive superiority studies or comprehensive dashboards.

This is a **synthetic planning illustration**, not a business recommendation for any actual project.

## Composition rule for a project-wide request

The planning skill supplies **route choice** only where genuinely unresolved. When a user has authorized an end-to-end execution outcome, the executor continues after the route is chosen, subject to genuine authority/integrity blockers. A needed architecture, research, specification or skill-engineering artifact retains its specialist owner. A planning checkpoint is not automatic approval, a new user interaction boundary or an obligation to make a permanent plan document.

**Forthcoming methods:** where skill-system evolution introduces an iterative semantic/independent-solution/prior-art/reconciliation/convergence cycle and Knowledge Delivery Strategy, treat those as **proposed upstream specialist methods** until a controlling installed version accepts them. Do not embed those prospective stages as unconditional planning prerequisites.

## Route-quality probes (not a new process gate)

On consequential routes, assess: (a) the first useful outcome is identifiable, (b) the next move is feasible under current authority/resources, (c) checkpoints are not activity theater, (d) distant uncertain work has no false granularity, (e) the plan preserves working baselines and existing accepted decisions, (f) a new material fact changes only affected route portions, and (g) a genuinely infeasible route is called out instead of masked by optimism.

Plan approval, source mutation and execution remain separate authority transitions. A planning-output test is not evidence of real runtime automatic routing.
