# Loom-foo — Functional skill IDs and primary families

Status: active private-package convention, version 1.0 (2026-11-14). Portable Agent Skills metadata convention; not an additional router, permission layer or parent-skill system.

## Identity and scope

- **Skill ID:** `loom-foo-<functional-role>` for *loom-foo-owned* skills. Use lowercase `a-z`, digits and single hyphens; no `--`, leading/trailing hyphen, or more than 64 characters. Match the skill folder and YAML `name` exactly. Choose names by the independently recognizable action/output; avoid an extra family segment (`loom-foo-writing-drafting`), a product/client/person name, and accidental rebranding of existing IDs. External/third-party skills retain their native identities.
- **Primary family:** `metadata.family` is **one string** describing the skill's principal competence. It is not part of the ID, package path, inheritance or activation route. Choose based on output owner, not matching keywords. Assign each installed skill to exactly one family; derive the count from the current source catalog.
- **Facets/related skills:** express material relationships in an explicit owner-boundary paragraph or `description` when needed. Do not introduce a second category/tags registry without a concrete consumer.
- **Distribution and state:** plugin/packaging, CORE/OPTIONAL/private/public selection, installed/discovered/loaded/tested status, and version/history are independent of `family`. A category does not create authority, permit private disclosure, force a skill-to-skill call or change plugin sharing.
- **Versioning:** taxonomy-only, nonbehavioral metadata on an existing skill need not bump that skill's own version. A meaningful change in skill-engineering's procedure does bump its own minor version. Bump the bundle independently for a new compatible portfolio capability.

## Families (semantic owners)

| Family | Owner of the primary result | Examples and boundaries |
| --- | --- | --- |
| `planning` | Problem framing, proposal, decisions, project/work/task planning, operational handoff | Includes handoff continuity; not execution of the work itself |
| `engineering` | Software/agent architecture, skill engineering, specification, change quality, failure diagnosis | No requirement that every engineering skill deals with code |
| `research` | Research design, collecting/reviewing evidence, transferring evidence-backed mechanisms | Collection and analysis remain distinct owners |
| `knowledge` | Intake, retrieval, interpretation of supplied links, durable knowledge consistency | No automatic access to private data or mutation |
| `writing` | Narrative organization, prose drafting, linguistic editorial review | Different output owners; no obligatory parent or chain |
| `design` | UX/UI, interaction, product and visual design artifact decisions | Design competence can overlap output formats with Writing without changing ownership |

## Assignment and lifecycle

1. Read current source `SKILL.md` and its positive/negative trigger and primary output. Choose exactly one of the six families; review true overlaps against owning siblings. If a new family is necessary, first justify a distinct recurring competence and update this reference and validator in the same change.
2. Keep the functional ID independent of grouping. A changed family normally requires only a metadata/documentation update; never rename a skill solely to regroup it.
3. Set `metadata.family: "<family>"` inside YAML frontmatter (string). Do not place an array at top level or invent `family` as a reserved Agent Skills field. Retain `name`, `description`, `version`, and existing runtime/authority semantics unchanged for classification-only updates.
4. Regenerate the **derived catalog** from the current SKILL.md metadata. Do not manually maintain a second mapping of skill-to-family outside the skill sources.
5. Run `python <plugin-root>/scripts/validate_skill_taxonomy.py --root . --check-catalog` from the plugin root. The checker checks source/YAML, grouping, ID/folder identity and catalog drift; it cannot prove host routing, quality or private publication readiness.
6. For any public export, separately exclude owner-private reference profiles and review contacts/manifest/disclosure. Family membership never substitutes a privacy filter.

## Current source of truth and limits

For the private plugin, each `skills/<skill-id>/SKILL.md` frontmatter is the family assignment authority. `docs/SKILL_FAMILIES.md` is generated by `<plugin-root>/scripts/validate_skill_taxonomy.py --catalog`, and must be reproducible. The validator has one allowed-family vocabulary; the table above explains meaning. `family` is a Loom-foo convention carried in open-standard `metadata`; clients are not required to expose or route by it. No fixed automatic family navigation UI is claimed.
